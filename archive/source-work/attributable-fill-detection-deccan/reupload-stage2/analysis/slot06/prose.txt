## What was wrong and what I changed

**Reading observations** (`fill_classifier.rs`)

1. **Window end** — `in_window` used `at <= start + ATTRIBUTION_WINDOW`. The interval is half-open, so an observation exactly at the end (a recycled identifier) was counted. Now `<`.
2. **Cumulative quantity** — `absorb_event` did `direct_filled += cumulative_filled_qty`, treating a running total as an increment, so every replay added. Now a high-water mark (`max`), which is also what makes the feed and the open-order list combine instead of double count.
3. **Ordering of a block's eligible set** — sorted by `order_id` alone; now (window start, `venue_seq`, `order_id`), the documented order.
4. **Remainder** — all units left by truncation went to the largest outstanding order; now one each to the first `r` orders in that ordering.
5. **Eligibility** — now excludes orders a block has already closed (a closed order contributes no outstanding quantity to a later basis) and de-duplicates an id repeated in `covers`. Finalization already covered every named order; it now also runs when the block is over the basis or empty.
6. **`locate`** — tried `order_id` before `client_ref`. Now `client_ref` first: it is the only key the engine always knows, the one a retry is made under, and the one that recovers a lost acknowledgement. `order_id` remains the fallback.

**Derived quantities** (`cycle.rs`)

7. **Residual exposure** — `close_gap` sized the corrective at `size − attributed`, ignoring quantity already working in committed neutralizations, so consecutive cycles sent the same exposure twice. Now `required − attributed − still working`, where an acknowledged corrective contributes its outstanding quantity, a lost-ack one its full size, and a finalized one nothing (the gap it leaves is real and gets covered once).
8. **Unconfirmed legs** — were neutralized against. Now never; the cycle returns instead of sending.
9. **Submission outcomes** — the record was dropped on *any* submit error, so a lost acknowledgement was retried under a fresh `client_ref` (a second economic order). Now: lost → keep the record, retry under the same reference; rejected/transport → drop it, so a later cycle recomputes and the mandate is not latched shut. The commitment is tracked in the ledger *before* the order is sent, so an unacknowledged order carries its original window start and its identity is recoverable from any later observation.
10. **Visibility** — a leg a block has closed is absent from `open_orders` and was not engine-cancelled, which the literal three-state reading calls "unconfirmed". I gave it its own known state: finality is exactly what makes its quantity knowable, and its residual is still covered. Plain absence (no block) is still unconfirmed and still never corrected against.

Durability needed no new `Snapshot` fields — the existing ones already cover window starts, cursor, attribution, finalized state, absorbed blocks, closure state, committed neutralizations and the reference sequence.

## One diagnostic I had to rewrite

`a_later_block_divides_over_the_residuals_of_the_earlier_one` expected a second block naming the *same two orders* to allocate over their residuals. That contradicts the contract's block-finality section, which states a finalized order "contributes no outstanding quantity to a later block's basis" — and it fails against the spec-correct implementation. I followed the documents (they are the stated authority; `tests/` is explicitly not graded) and replaced it with four checks that separate the two rules it conflated: finality, later blocks over orders the earlier one did not name, and finalization of orders the division skipped.
